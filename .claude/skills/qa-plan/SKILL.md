# QA 계획 생성

스프린트, 기능, 개별 스토리에 대한 구조화된 QA 계획을 생성한다.
구현 전에 실행하여 팀이 테스트 요구사항을 사전에 파악할 수 있도록 한다.

## Phase 1: 범위 파악

인수에 따라 범위 결정:
- **`sprint`**: 현재 스프린트 계획 (`Md/Plans/` 내 최신 파일) 읽기
- **`feature: [system-name]`**: 해당 시스템 관련 파일 검색
- **인수 없음**: AskUserQuestion으로 범위 질문

## Phase 2: 스토리 분류

각 스토리를 테스트 유형으로 분류:

| 스토리 유형 | 분류 기준 |
|------------|----------|
| **Logic** | 계산, 공식, 수치 임계값, 상태 전환 |
| **Integration** | 두 개 이상 시스템 상호작용, 이벤트 전파 |
| **Visual/Feel** | 애니메이션, VFX, 셰이더, 반응성, 타이밍 |
| **UI** | 메뉴, HUD, 버튼, 화면, 인벤토리 패널 |

## Phase 3: QA 계획 문서 생성

```markdown
# QA 계획: [스프린트/기능명]
**날짜**: [date]
**범위**: [N개 스토리]

## 테스트 요약

| 스토리 | 유형 | 자동화 테스트 필요 | 수동 검증 필요 |
|--------|------|-----------------|---------------|

## 자동화 테스트 필요 항목

### [스토리 제목] — [유형]
**테스트 대상**:
- [GDD의 공식 또는 규칙]
- [각 상태 전환 또는 결정 분기]

**엣지 케이스**:
- 최솟값/최댓값 입력
- 널/잘못된 입력

## 수동 QA 체크리스트

### [스토리 제목] — [유형]
**검증 방법**: [스크린샷/플레이테스트/단계별 확인]
**승인자**: [담당자]

체크리스트:
- [ ] [구체적이고 반증 가능한 조건]

## 스모크 테스트 범위

1. 게임 실행 및 정상 시작
2. 신규 세션 시작 가능
3. [이번 스프린트에서 변경된 주요 기능]
4. [리그레션 위험이 있는 시스템]

## 완료 정의

- [ ] 모든 완료 기준이 자동화 테스트 결과 또는 수동 검증으로 확인됨
- [ ] Logic/Integration 스토리에 테스트 파일 존재
- [ ] Visual/Feel 및 UI 스토리에 수동 검증 증거 존재
- [ ] 리그레션 없음 확인
```

## Phase 4: 저장

계획을 보여준 후 사용자 승인을 요청한다.
승인 시 `Md/Plans/QA_Plan_[sprint-slug]_[YYYYMMDD].md` 에 저장.
